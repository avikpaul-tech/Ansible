# Ansible Ad-Hoc Commands Reference for Oracle DBAs

Ansible ad-hoc commands are single, one-line operations executed from the control node against one or more managed database nodes. They are best suited for quick health checks, emergency triage, one-time script executions, and gathering diagnostic data without writing a full playbook.

---

## 1. Anatomy of an Ad-Hoc Command

```bash
ansible <host-pattern> -m <module_name> -a "<arguments>" [privilege_escalation_flags]

```

### Essential Flags

| Flag | Long Option | Description |
| --- | --- | --- |
| `<host-pattern>` | `all`, `db_servers`, etc. | Target host, group, or IP defined in your Ansible inventory. |
| `-m` | `--module-name` | The module to execute (e.g., `ansible.builtin.command`, `ansible.builtin.shell`, `ansible.builtin.copy`, `ansible.builtin.script`). Default is `ansible.builtin.command`. |
| `-a` | `--args` | The arguments or commands to pass to the module. |
| `-b` | `--become` | Enables privilege escalation (`sudo`). |
| `--become-user` |  | The target OS user to escalate to (e.g., `oracle` or `root`). Default is `root`. |
| `-u` | `--user` | Remote SSH connection user (e.g., `ansible`). Default is defined in `ansible.cfg`. |
| `-i` | `--inventory` | Path to the inventory file (if not using the default path). |

## 2. Primary Modules for DBA Tasks

### A. `ansible.builtin.command`

Directly executes binaries on remote targets without invoking a system shell. Fast and safe from shell parsing issues.

* **Rule:** Use for fixed utilities and standalone scripts. Pipes (`|`), redirections (`>`), and shell variables (`$ORACLE_HOME`) are **not** supported.
* **Basic Syntax:**
```bash
ansible all -m ansible.builtin.command -a "<path_to_binary_or_script> <args>" -b --become-user=oracle

```



### B. `ansible.builtin.shell`

Executes commands through the remote host's shell (`/bin/sh`).

* **Rule:** Use when commands require piping (`grep`, `awk`), redirects (`>>`), compound logic (`&&`), or environment variable evaluation.
* **Basic Syntax:**
```bash
ansible all -m ansible.builtin.shell -a "<command_with_pipes_or_redirection>" -b --become-user=oracle

```



### C. `ansible.builtin.script`

Takes a script stored locally on the control node, copies it to a temporary directory on the managed nodes, executes it, and removes the temporary file.

* **Rule:** Use when a diagnostic or deployment script exists **only on the control node** and you do not want to pre-copy it to every server.
* **Basic Syntax:**
```bash
ansible all -m ansible.builtin.script -a "/path/on/control_node/script.sh" -b --become-user=oracle

```



### D. `ansible.builtin.copy`

Transfers files from the control node to managed nodes and establishes ownership and permissions.

* **Rule:** Use to push static files, configuration templates, or persistent scripts to remote directories like `/home/oracle`.
* **Basic Syntax:**
```bash
ansible all -m ansible.builtin.copy -a "src=/local/path/file dest=/remote/path/file owner=oracle group=oinstall mode='0755'" -b --become-user=oracle

```

## 3. Practical Oracle DBA Ad-Hoc Scenarios

### Scenario 1: Listener & Service Status (`command`)

Check the Oracle TNS listener status across all database nodes:

```bash
ansible all -m ansible.builtin.command \
  -a "/u01/app/oracle/product/19.0.0/dbhome_1/bin/lsnrctl status" \
  -b --become-user=oracle

```

### Scenario 2: Active Oracle Background Process Verification (`shell`)

Check if database PMON processes are active across nodes using pipe filters:

```bash
ansible all -m ansible.builtin.shell \
  -a "ps -ef | grep pmon | grep -v grep" \
  -b --become-user=oracle

```

### Scenario 3: Push a Script to Managed Node Home Directory (`copy`)

Deploy a reusable maintenance script from the control node to `/home/oracle`:

```bash
ansible all -m ansible.builtin.copy \
  -a "src=/tmp/db_prechecks.sh dest=/home/oracle/db_prechecks.sh owner=oracle group=oinstall mode='0755'" \
  -b --become-user=oracle

```

### Scenario 4: Run a Local Control Node Script Remotely (`script`)

Execute a local control node script across target nodes without copying it permanently:

```bash
ansible all -m ansible.builtin.script \
  -a "/tmp/node_check.sh" \
  -b --become-user=oracle

```

### Scenario 5: Disk Space Pre-Checks on Oracle Mount Points (`command`)

Inspect available space on `/u01` and Fast Recovery Area (FRA) filesystems:

```bash
ansible all -m ansible.builtin.command \
  -a "df -h /u01" \
  -b --become-user=oracle

```

## 4. Controlling Terminal Output (Suppressing JSON Noise)

By default, Ansible ad-hoc commands output raw JSON containing `\r\n` linebreaks. To format output as clean, human-readable terminal text:

* **Temporary (Per-Command Override):**
Prefix the command with `ANSIBLE_STDOUT_CALLBACK=debug` or `ANSIBLE_STDOUT_CALLBACK=yaml`:
```bash
ANSIBLE_STDOUT_CALLBACK=debug ansible all -m ansible.builtin.script -a "/tmp/node_check.sh" -b --become-user=oracle

```


* **Permanent (`ansible.cfg` Setting):**
Add the callback to your control node's `ansible.cfg`:
```ini
[defaults]
stdout_callback = debug

```
